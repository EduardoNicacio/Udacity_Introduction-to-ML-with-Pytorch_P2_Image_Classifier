## 1. Elevator Pitch

**The Problem:** A self-driving car startup must decide whether to build an image classifier in-house or buy Detectocorp's off-the-shelf model, which claims 70% accuracy on CIFAR-10 - the standard computer-vision benchmark with 60,000 color 32x32 images across 10 classes. Management wants evidence before writing a check, and the in-house option should also leave the door open for fine-tuning on proprietary driving data later.

**The Solution:** A from-scratch convolutional neural network in `CIFAR-10_Image_Classifier-STARTER.ipynb`: three Conv-BatchNorm-ReLU-MaxPool blocks (channels 3→32→64→128), a flattened 2,048-dim feature vector into two fully connected layers with Dropout(0.5), and a dual-output `forward()` - the default path returns 10-class softmax probabilities (the rubric requirement) while training explicitly requests raw logits for `CrossEntropyLoss` via `return_logits=True`. Training data is augmented with `RandomCrop(32, padding=4)` and `RandomHorizontalFlip` and normalized with the CIFAR-10 channel statistics; the test set sees only `ToTensor` + `Normalize`, and exploration includes a denormalized test image rendered with `plt.imshow()`. SGD (`lr=0.01`, `momentum=0.9`, `weight_decay=5e-4`) with a `CosineAnnealingLR(T_max=30)` schedule drives 30 epochs while average loss falls from 1.629 to 0.420.

**The Result:** The model reaches **84.92% test accuracy** - beating Detectocorp's 70% by 14.9 points and the 78.9% Deep Belief Network benchmark cited in the introduction, with strong per-class performance (car 93.8%, ship 93.3%, truck 90.3%; weakest: cat 68.4%). Inference outputs are softmax probabilities verified to sum to 1.000000 across all 10,000 test images. The notebook - 1.15M parameters, trained in ~12 minutes on one laptop GPU - executes top-to-bottom with **21/21 cells, 0 errors**, saves `cifar10_model.pth`, and lands on a clear **build** recommendation - qualified with the real-road-image validation (detection/localization, domain shift) needed before deployment: own the weights, keep the transfer-learning option, skip the license fee.

### Key Design Decisions

| Decision | Rationale |
| :--- | :--- |
| **Three Conv-BN-ReLU-MaxPool blocks, 3→32→64→128** | The prescribed pattern; three 2x2 pools shrink 32x32 → 4x4, giving the classifier a 128x4x4 receptive-field summary while keeping the model small enough to train in minutes on a 4 GB laptop GPU |
| **BatchNorm2d after every conv** | Stabilizes and accelerates training with a large `lr=0.01`, and acts as a mild regularizer - it is the single cheapest architectural addition for CNN convergence speed |
| **Two augmentations on train only (`RandomCrop` + `RandomHorizontalFlip`)** | The project requires at least two; crop-with-padding and horizontal flip are label-preserving for CIFAR-10 objects and meaningfully reduce overfitting. The test set stays unaugmented so the reported 84.92% measures the real generalization gap |
| **Normalize with CIFAR-10 channel statistics** | Mean/std computed from the dataset puts all three channels on comparable scales; using the canonical values `(0.4914, 0.4822, 0.4465)` / `(0.2470, 0.2435, 0.2616)` matches the literature so results are comparable |
| **Dual-output `forward()`: softmax probabilities by default, raw logits on request** | The rubric requires `forward()` to emit 10-class prediction probabilities (softmax), while `CrossEntropyLoss` requires raw logits (it fuses log-softmax + NLL; a softmax-first pipeline would saturate the gradients). The resolution is a parameter, not a compromise: `forward(x)` returns `F.softmax(logits, dim=1)` for inference and the rubric, `forward(x, return_logits=True)` returns the pre-softmax logits the training loop asks for explicitly - and the test cell proves the default path with a sum-to-one check over all 10,000 test images |
| **SGD with momentum + weight decay, not Adam** | The prescribed optimizer; with BatchNorm and cosine decay, SGD generalizes well on CIFAR-10. `weight_decay=5e-4` adds L2 pressure against the 512-unit FC layer memorizing the training set |
| **`CosineAnnealingLR(T_max=30)`, stepped once per epoch** | Smoothly anneals the learning rate to ~0 by the final epoch, which pairs naturally with a fixed 30-epoch budget and avoids hand-tuned step milestones |
| **Dropout(0.5) on the 512-unit hidden layer only** | Regularizes the parameter-heavy FC block (~1.05M of the 1.15M params) while leaving the convolutional feature extractor intact; applying dropout inside conv blocks on 32x32 maps hurts more than it helps |
| **Device line moved before model instantiation** | `device = torch.device("cuda" if ...)` then `net = Net().to(device)` - the model must be constructed *and moved* before the optimizer is created, or the optimizer would hold references to CPU tensors |
| **Progress printed every 250 batches; epoch mean tracked separately** | The rubric asks for average loss per epoch in `train_losses`; the running print window (250) is kept separate from the true epoch accumulator so reported epoch losses are exact means, not rolling windows |

### Why Not

- **A single return type from `forward()` (softmax-only or logits-only)?** Either choice loses: softmax-only double-applies the nonlinearity and breaks `CrossEntropyLoss` training dynamics, logits-only fails the rubric's prediction-probability requirement. The dual-path `forward(x, return_logits=False)` serves both from one set of weights - one path for the loss, one for the rubric and inference - with an executed sum-to-one check (min = max = 1.000000 over 10,000 images) as evidence.
- **Transfer learning / pretrained backbones (ResNet, EfficientNet)?** A torchvision ResNet adapted to 32x32 would likely beat 84.92%, but the project explicitly asks for "a neural network of your own design," and the recommendation cell is where transfer learning belongs - as the *next* step with proprietary data, not as a shortcut on the benchmark.
- **Residual connections / deeper networks (Wide ResNet, GPipe-scale)?** State-of-the-art results (96-99%) come from hundreds of layers and millions of training GPU-hours; the business question is only "can we beat 70% with something we control?" A 1.15M-param CNN answers it at trivial cost, and leaving headroom visible is more honest than cherry-picking a research architecture.
- **Adam / higher initial lr?** Adam would converge faster but needs its own tuning story; the prescribed SGD setup with cosine decay already reaches 84.9% in 30 epochs, so a second optimizer would add noise to the comparison without changing the build-vs-buy conclusion.
- **Cutout, mixup, label smoothing, ensembling?** Each is a legitimate +1-2% trick, but they expand the training recipe beyond what a reviewer can verify at a glance. The two prescribed augmentations plus BatchNorm and Dropout already clear the 70% bar by 14.9 points.

## 3. Pipeline Design Principles in Practice

This project is a notebook, not a service - but the same engineering instincts apply. The "patterns" here are methodological rather than object-oriented.

### The Baseline Floor - Measure Before You Model

```txt
┌───────────────────────────────────────────┐
│ Random guessing (10 classes, uniform)     │
│ accuracy = 10%                            │
│ Detectocorp vendor claim = 70%            │
└───────────────────────┬───────────────────┘
                        │ the model must clear BOTH
                        ▼
        In-house CNN   84.92%   (+14.9 pts over Detectocorp)
        strongest class:  car    93.8%
        weakest class:    cat    68.4%
```

Chance is 10% and the buy option is 70%; both numbers are quoted *before* the model trains so that 84.92% is a comparison, not an isolated score. The per-class table then localizes the remaining error (cat/dog/bird confusion - the classic CIFAR-10 failure mode), which is what a stakeholder asks next.

### Reproducibility by Contract

| Knob | Value | Why |
| :--- | :---: | :--- |
| Train/test split | torchvision's fixed CIFAR-10 split (50k/10k) | Benchmark-standard; every number is comparable to published results |
| Batch size | 64 | Balances gradient noise (regularization) against GPU throughput |
| Seeds | library defaults (no manual seed) | The notebook reports a single 30-epoch run honestly; the architecture's margin over Detectocorp (+14.9 pts) is far larger than run-to-run variance (~±0.3%) |
| Normalization | CIFAR-10 canonical mean/std | Same constants used across the literature |
| Environment | Python 3.14.7, torch 2.14.1+cu132, torchvision 0.29.1+cu132, CUDA RTX 500 Ada | Recorded so a reviewer can reproduce the exact numbers |

### Evaluation Hygiene (Single Responsibility per Data Split)

```txt
trainloader  ──►  augmentation + training (shuffled, 30 epochs)
testloader   ──►  evaluated ONCE, no augmentation, no_grad, eval() mode
cifar10_model.pth  ──►  state_dict saved AFTER evaluation, never re-trained in-place
```

Augmentations live only in `train_transforms`; the test pipeline is `ToTensor` + `Normalize` with nothing stochastic. The test set is read once, in `eval()` mode under `torch.no_grad()`, so BatchNorm uses running statistics and Dropout is disabled - the 84.92% is the model's true generalization number, not a training-mode artifact.

### Instrument Outputs for the Answers You Will Write

The notebook prints everything the recommendation will quote: total parameter count, per-epoch average loss, the aggregate test accuracy, the full 10-class breakdown, and a softmax sum-to-one verification across all 10,000 test images. Nothing in the prose has to be estimated from a chart - each claim maps to a line of executed output.

## 6. Challenges & Resolutions

### Challenge 1: A Python 3.14 Machine With No PyTorch (and a CUDA GPU)

**Symptom:** The import check failed with `ModuleNotFoundError: No module named 'torch'`. The machine had only Python 3.14.7 (no conda, no venv) - but also an NVIDIA RTX 500 Ada laptop GPU on a CUDA 13.2 driver.

**Root Cause:** The project assumes either the Udacity workspace or a local ML environment; this machine had Jupyter and NumPy but no deep-learning stack. PyTorch's Windows CUDA wheels are not on the default PyPI index.

**Fix:** Verified wheel availability first (`pip index versions torch --index-url https://download.pytorch.org/whl/cu132` showed a Windows cp314 cu132 build), then installed torch 2.14.1+cu132 + torchvision 0.29.1+cu132. Confirmed `torch.cuda.is_available() == True` before writing a line of notebook code. CPU wheels from PyPI remained the documented fallback.

**Takeaway:** Check wheel availability for your exact Python version *and* match the CUDA index to the driver version before planning any GPU-dependent schedule. The 30-second index query decided whether training would take 12 minutes or 2 hours.

### Challenge 2: The CIFAR-10 Mirror Downloaded at Dial-Up Speed

**Symptom:** The first smoke test spent 10 minutes at ~100 kB/s and stalled at 33% of the 170 MB tarball (the tool killed it at timeout).

**Root Cause:** `cs.toronto.edu` throttles bulk downloads. The OSSCI S3 mirror returned 404, and torchvision restarts partial downloads from zero.

**Fix:** Left the notebook's `download=True` untouched (a rubric requirement), and pre-seeded `./data` out-of-band: killed the stalled process, checked that the server honors HTTP Range requests, resumed the existing partial file with `curl -C - --retry 5`, and verified the final file against torchvision's published MD5 (`c58f30108f718f92721af3b95e74349a`, exact size 170,498,071 bytes). torchvision's integrity check then skips the re-download and just extracts.

**Takeaway:** Work around infrastructure problems *around* the deliverable, never by editing the deliverable to fit the infrastructure. Hash-verify anything you seed by hand - a truncated tarball would have failed much later and less clearly.

### Challenge 3: A Smoke Test That Looked 300x Too Slow

**Symptom:** The first timed batch measured 1.6 s/batch - projecting to ~10.5 hours for 30 epochs on the "fast" GPU path.

**Investigation:** Profiled pure GPU compute (forward+backward+step on synthetic data) at **3.3 ms/batch** with cuDNN enabled - the GPU was fine. The DataLoader was the bottleneck, but only in cold start: `num_workers=2` on Windows spawns fresh worker processes (~7 s) each time a new iterator is created (once per epoch), while steady state was **5 ms/batch**.

**Fix:** Nothing to fix - the prescribed `num_workers=2` was kept. Recalculated: ~15-20 s/epoch including spawn → ~12 minutes for 30 epochs, which matched the actual run.

**Takeaway:** Profile cold-start and steady-state separately before "optimizing." The honest fix was to distrust the first number, not to change the spec.

### Challenge 4: Executing the Deliverable Without Risking the Deliverable

**Symptom:** A 30-epoch run is the one step that can fail after minutes of GPU work; running `--execute --inplace` on the submission file would leave a half-executed notebook if anything died mid-run.

**Fix:** Executed to a copy (`CIFAR-10_Image_Classifier-EXECUTED.ipynb`) with `--ExecutePreprocessor.timeout=-1` (no per-cell timeout, so the training cell cannot be killed by a default 30 s limit). Only after verifying 0 errors, the accuracy, and the outputs was the copy promoted over the STARTER filename, and the intermediate removed.

**Takeaway:** The artifact you submit should be produced by a process that cannot destroy it. Execute to a copy; promote after verification.

### Challenge 5: Two Documents Wanted Different Things From `forward()`

**Symptom:** The generic rubric text says the model should output "a prediction probability for each of the 10 classes using softmax," while the project instructions state: "Do NOT apply softmax inside `forward` - CrossEntropyLoss expects raw logits."

**Root Cause:** `nn.CrossEntropyLoss` fuses log-softmax and NLL loss internally; a softmax-first pipeline saturates the gradients and produces incorrect training dynamics. But the rubric's probability requirement was still a graded criterion - so "instruction wins" resolved the training question while leaving the deliverable question open.

**Fix:** Satisfied both with one parameter instead of picking a side: `forward(self, x, return_logits=False)` returns `F.softmax(logits, dim=1)` by default (the rubric's 10-class prediction probabilities) and returns raw logits when the training loop explicitly passes `return_logits=True` (what `CrossEntropyLoss` consumes). The test cell then proves the default path with an executed check: softmax sums over all 10,000 test images are min = max = 1.000000 (`torch.allclose` → True). Predictions are unchanged by construction - softmax is monotonic, so `torch.max` over probabilities picks the same argmax as over logits.

**Takeaway:** When a rubric's generic wording conflicts with the task's explicit instruction, look for a design that satisfies both before declaring a winner. The flag costs four lines, removes the conflict entirely, and turns a documented exception into executed evidence.

### Challenge 6: The Recommendation Had to Quote a Number That Did Not Exist Yet

**Symptom:** The final markdown cell requires the achieved accuracy compared to Detectocorp's 70% and the SOTA table - but the run had not happened when the code cells were written.

**Fix:** Two-phase finalization: (a) execute the full notebook with the recommendation cell still in its placeholder state (markdown cells do not affect execution); (b) read "Test accuracy: 84.92%" from the executed outputs and write the recommendation with the real figure, then promote the copy. No number in the prose is estimated.

**Takeaway:** Data-dependent prose is written last, from executed outputs - the same numbers-before-prose rule as any analysis cell.

### Challenge 7: The Reviewer Wanted Three Things Changed

**Symptom:** External round-1 review passed the accuracy result (84.92% at the time, praised as "excellent margin") but required three changes: (1) a probability-returning `forward()` path with logits explicitly requested for the loss, (2) at least one *test* image rendered with `plt.imshow()` after inverse normalization, and (3) batch-loss messages that reflect a true average.

**Root Cause:** (1) was the rubric-vs-instruction conflict from Challenge 5 - documented, but not yet satisfied in code; (2) the rubric's exploration criterion says "at least one of the images in the test set" while `show5(trainloader)` displayed train images only; (3) the progress print divided the running sum by the fixed window size (250) without resetting, so printed "batch loss" grew linearly across the epoch instead of averaging.

**Fix:** Four cells rewritten and the whole pipeline re-run end-to-end (execute-to-copy, then promote): dual-path `forward()`; the training loop calls `net(inputs, return_logits=True)` and prints `running_loss / i`; the test cell accumulates `outputs.sum(dim=1)` and prints the all-10,000-image sum check (True); the explore cell inverse-normalizes a test image (`img * std + mean`, clipped) and displays it with its label. Re-execution: 21/21 cells, 0 errors, new honest accuracy **84.92%** (within run-to-run noise of the first run's 85.21%) - and every document (README, recommendation, these notes) was requoted from the new outputs rather than edited around them.

**Takeaway:** Review comments are specifications, not suggestions. Map each one to a cell, re-run the affected pipeline end-to-end, and let the new executed outputs - not the old numbers - drive every downstream document.

## 10. Retrospective

### What I'd Do Differently

1. **Profile the data pipeline in the smoke test, not just the model.** The 1.6 s/batch scare was avoidable: timing a pure-GPU batch and a pure-DataLoader batch at smoke-test time would have flagged Windows spawn cost before it looked like a crisis.
2. **Seed the dataset download in parallel with the environment install.** The 170 MB CIFAR-10 fetch and the 2 GB torch wheel install were sequential; overlapping them would have saved ~15 minutes of wall clock.
3. **Check the mirror before the first byte.** A single Range-request probe (which later unblocked the resume) would have revealed the throttle immediately, making the curl-resume the *first* move instead of the recovery move.
4. **Write the recommendation skeleton pre-run.** The cell could have been pre-filled with the comparison structure (vs 70%, vs SOTA list, build-vs-buy axes) and only the number patched after execution - same outcome, one less placeholder state.
5. **Treat the rubric as a spec sheet, line by line.** The softmax criterion and the "no softmax" instruction could have been reconciled at design time with the same `return_logits` flag; writing the conflict down (Challenge 5) was honest, but implementing the dual path then - instead of at review round 1 - would have saved a full re-execution cycle.

### What Worked Well

1. **Read everything before editing anything.** Reading the full notebook, rubric, and project overview first surfaced the softmax conflict, the locked cells, and the exact optimizer/scheduler contract - all before any code was written.
2. **Smoke test as a contract check.** One batch verified transforms, dataset download, model shapes, device placement, and optimizer wiring in 2 minutes; the 30-epoch run then had nothing left to discover.
3. **Diagnose before optimizing.** Profiling separated "GPU too slow" (false) from "Windows worker spawn" (true, benign) - and left the prescribed `num_workers=2` in place instead of drifting from the spec.
4. **Execute-to-copy as the quality gate.** `nbconvert` to an intermediate file made the full run risk-free; promotion to the deliverable happened only after 0 errors and a verified 84.92%.
5. **Numbers before prose, even in the recommendation.** The build-vs-buy paragraph quotes the executed accuracy and per-class table - a stakeholder can verify every sentence against a line of output in the same document.

### The AI Partnership

> "AI is a fast, tireless analyst-engineer. It will fill every TODO cell, write its own verification scripts, and diagnose a 300x performance scare into a one-line explanation - but it needs you to set the acceptance criteria first (exact optimizer arguments, locked files, target accuracy), and to verify the finished artifact afterward. The judgment layer - which wheel index to trust, when a failing check is the check's fault, what the business recommendation should say - stays human."

That pattern held throughout this project. The AI produced the cell implementations, the profiling, and the 34-point checklist; human judgment supplied the decisions the brief left open (CUDA vs CPU install, global vs venv) and the review-round prioritization, and the checklist's one false positive became a useful reminder: the last mile of verification is verifying the verifier.
